# UniApp Jest, jsdom and scoped once boundary

The locked developer dependency `@dcloudio/uni-automator` `3.0.0-4020920240930001` declares `jest` `27.0.4` as a peer. The installed Jest tree includes `jest-cli`/`jest-config`/`jest-runner` `27.5.1` → `jest-environment-jsdom` `27.5.1` → `jsdom` `16.7.0` → `http-proxy-agent` `4.0.1` → `@tootallnate/once` `1.1.2`. This scoped package is separate from the unscoped `once` package elsewhere in the lock. The old versions remain installed; this audit changes no dependencies or application code.

The current UniApp scripts and Linux CI use Node's `node --test`, not Jest. The real locked Jest `--showConfig` defaults to `jest-environment-node`, with empty `testEnvironmentOptions`. There is no first-party Jest config or import of the jsdom/proxy/once chain. Loading the actual automator package, Vite plugin and Uni CLI help does not load Jest, jsdom, the proxy agent or scoped once. A control import of `jsdom` does load the proxy agent and scoped once, so the module-cache check is sensitive to this path. These probes block HTTP and TCP connection attempts and start no server.

The installed jsdom environment lazily creates a `JSDOM` with `runScripts: 'dangerously'` if a future test selects it. jsdom imports its HTTP proxy agent when the module is loaded. That agent imports `@tootallnate/once`, but calls it only when opening a proxy socket. Current tests do not select that environment or feed it HTML/resources, and current app builds have no Jest/jsdom/once module in the H5, Weixin, App-vue or App-nvue Rollup graphs. Enabling Jest with jsdom, importing these modules in first-party code, changing the lock/entrypoints, or adding another build target requires a new review of scripts, external resources and proxy behavior.

Run `npm run test:jest-jsdom-once` in `view/uniapp-ts` after `npm ci`. The test checks the exact lock and installed packages, current scripts and imports, actual Jest configuration, real CLI module loading with a positive control, and a real Rollup external-module failure. The existing `npm run test:runtime-i18n` runs isolated H5, Weixin and App builds and now rejects this chain even when an ID is external or tree-shaken. CI runs both. A green result is limited to these source paths and build targets; it does not validate the library versions as safe, an automator E2E, a future Jest/jsdom runner, other mini-program targets, HBuilderX/native baselines, or production devices. TEST-004D3 remains open.
