# Customer profile compatibility contract

This slice ports the customer personal-data form from fixed PHP `8ed2a5b139f9170dd11b0dff91803f2fd59e40a5`: `User.php::edit`, `UserServices::{handelExtendInfo,saveExtendForm,userInfo}` and `view/uniapp/pages/users/user_info/index.vue`. It does not implement account cancellation, phone binding, password changes, membership activation, or a new generic attachment capability.

## Read and save

`GET /api/user/info` retains its existing eleven-key DTO. Only canonical avatar references are resolved under the persisted UID authority and signed; other existing avatar strings remain unchanged in this legacy DTO. `GET /api/user/info?profile=1` opts into `{actor_uid,revision,version,profile}`. The profile contains `uid,account,nickname,avatar,avatar_preview,phone,register_extend_info,extend_info`. Stable avatar identity and signed preview are separate. Both GET forms are private/no-store and execute within one repeatable-read/read-only snapshot. Query `profile` must be a single literal `1` if present. Unrelated legacy query keys never select an owner.

Modern `POST /api/user/edit` accepts exactly `{profile:1,revision,version,nickname,avatar,extend_info:[{info,value}]}` and returns the existing successful null data. Old nickname/avatar partial calls remain accepted; an empty legacy avatar is ignored, and an empty nickname can accompany a nonempty avatar. Empty/no-op requests do not issue an UPDATE. Modern nickname input retains raw text up to255 Unicode characters for comparison with the persisted value: an exactly unchanged historical nickname is preserved, including whitespace or a length greater than16; only a genuinely changed nickname is trimmed and limited to16. Blank modern nicknames are rejected. Legacy partial nickname edits retain the original trim/16 grammar. Extra fields and duplicate decoded JSON keys at any depth are rejected before business work; UTF-8 body is bounded to64KiB.

The template is the current platform `user_extend_info` winner by sort/id, including its raw value in revision. All source definitions are validated, without truncation: max64, unique names/nonempty standard mappings, eight known formats, max32 unique radio choices. Only `use=1 && user_show=1` definitions are editable. A missing/falsey/empty template exposes no editable extension fields; it never clears existing fields. Invalid or ambiguous templates produce a visible business error. The submission must cover exactly the visible server names; clients cannot change definitions, mappings or hidden fields. Each submitted extension value is at most4096 characters for existing-value compatibility; a genuinely changed value must fit1024. Required blank values still fail. Unchanged legacy values (including invalid format, whitespace or nonmidnight birthday seconds) bypass normalization and are preserved byte-for-byte; only changed fields enter the audited normalizer/date codec.

Profile values are exposed as strings. Radio values use PHP zero-based index strings; incoming exact option labels and numeric values are accepted by the existing audited activation-field normalizer and stored canonically as index strings. Dates are strict YYYY-MM-DD, real dates and persisted signed-int4 uniquely resolved Asia/Shanghai-midnight seconds (historical DST included). All eight formats use the existing normalizer, but the activation-only `level_extend_info` column is never written. Standard mappings are `real_name→real_name`, `sex→sex`, `birthday→birthday`, `card_id→card_id`, `address→addres`, `mark→mark`. Empty editable standard fields clear their own columns. Reads take these values from authoritative columns; custom values match stored `info`. Nonvisible, removed and unknown stored metadata/values remain intact; unchanged original serialized extension bytes are not rewritten. Complete resulting extension JSON is bounded to32KiB.

The write locks the current user, rechecks active/nondeleted/password identity and compares the profile version; the version includes current profile/standard columns but excludes financial balances. It takes shared locks on all present platform template-source rows, checks template revision, validates everything, then changes only differing user columns. Profile/template conflicts return body.status409; concurrent profile changes are rejected rather than merged over a stale read. No new audit/history/reward/business/cache writes or automatic replay are added. A concurrent insertion of a new template winner is serialized only at the transaction read point; no global config-writer fence is claimed.

## Avatar authority and public chain

A replacement must be a canonical attachment actually uploaded into the current UID's registered-user scope: type3/relationIdUID/module3/file1/R2image8, matching att_dir, raster MIME/extension, and exact `attachments/user/UID/` namespace without traversal. Its metadata row is locked while saving. Existing unchanged static/HTTPS or platform defaults can survive unrelated edits; a copied ticket never authorizes a replacement. Signing occurs after the database transaction and does not perform HTTP/R2 I/O. Profile reads reuse the existing public PinkAvatarMediaPolicy, which already supports this exact user ownership. The public user-centre and customer-work projections also already support that namespace and are unchanged. Registered HTTP tests exercise actual `/api/pink`, `/userinfo`, `/community/user_info/11` and `/api/assets` following profile save; AttachmentService upload is also real. The shared user-avatar resolver bounds the complete batch at1000, performs one metadata query, preserves exact prior user/platform raster authority, and leaves the public Pink endpoint at its original max3. Platform fallback derives type/relation/module from adminAttachmentScope(), not guessed numeric types. The canonical-followup consumer wrapper preserves legacy noncanonical relative/static/HTTPS values verbatim; it only resolves and signs canonical capabilities, so adopting this repair cannot silently erase historical relative strings. Existing self-profile, bargain-help, community registered-user profiles, agent directory, lottery-winner and membership-home DTOs receive narrow UID-bound media projections. Lottery/member-home current UI does not display these avatar DTO fields, so no such visual claim is made.

Remaining visible user-avatar chains were inspected before the final validation. The spread-poster data service already authorizes a user-owned avatar separately from platform poster templates, and its existing policy remains unchanged. DIY `userInfor`, review-detail author/current-user slots and review comments now apply the same bounded persisted-UID authorization. Review-detail keeps its existing single views counter increment and the UID0 platform review media policy; pictures are unchanged. The comment DTO still returns only its first already-ordered child per root. The same picked-child map drives media resolution and serialization, so at most200 displayed slots are considered; canonical `(UID, reference)` pairs are deduplicated and legacy strings do not consume new capability budget. Undisplayed children are not authorized or removed. Real registered HTTP regressions include more than1000 legacy/repeated/distinct-undisplayed child references. The general resolver remains bounded at1000 distinct canonical slots and never truncates. Review-list/product-detail summary UI currently uses nickname initials instead of its avatar DTO; no visible list-avatar repair is claimed and its existing media policy remains unchanged.

## Validation scope

`test/customer-profile-postgres.test.ts` uses real registered createApp/JWT/routes and ORM SQL. Ordinary runs use owned PGlite; the local finance runner can select disposable PG16. The fixture is DI-provided and does not prove a separate production LOGIN ACL, production Redis enrollment, a login form, or all public-avatar consumers. It snapshots all owned tables/sequences and object/queue calls around reads/rejections, and checks exact allowed user-column deltas for successful saves. Browser/client upload/navigation and build checks are coordinated separately.
