# Supplier 商品赠送积分

本批将供应商商品的 `give_integral` 接通到现代编辑器及普通保存 API，覆盖当前实物、卡密/固定内容、手工虚拟三类商品（0、1、3）。使用现有订单创建、支付分配、收货奖励和退款服务验证实际结果；不改写这些消费者。

## 固定旧版依据

PHP 固定提交为 `8ed2a5b139f9170dd11b0dff91803f2fd59e40a5`。`supplier/product/StoreProduct::save` 接收 `give_integral`，通用商品服务保存该列。`StoreOrderCreateServices` 按商品积分乘该行数量、BCMath scale=0 计算 `gain_integral`；`StoreOrderTakeServices::gainUserIntegral` 仅向普通订单发放商品积分，时间为确认收货。预售等营销订单不发放此积分，付费会员的实付返积分倍率也不放大商品积分。四份实际读取的旧文件均与固定提交完整字节一致，摘要见审计清单。

## 保存与读取

明确提供 `give_integral` 时接受字符串或数字的非负十进制，整数最多十位、小数最多两位，与现有 `decimal(12,2)` 列匹配。不采用浮点四舍五入；规范化为两位小数字符串。明确 0 清空奖励。null、空字符串、布尔、数组、对象、负数、科学记数法字符串、精度或范围超限均拒绝。省略及 undefined 保留旧值，并不进入该列的 SQL UPDATE 目标；新建省略使用既有数据库默认值。

明确积分作者要求当前 Supplier 商品管理权限，沿用分类范围锁、产品写锁及已有超时。普通保存仍整体待审核且下架。所有作者及延迟约束执行后，再核对当前登录权限、实际所有权、履约类型、删除/显示/审核状态以及最终积分。真实触发器跳过、改值、延迟改归属/显示/类型或撤销管理权限都会使全部业务写入回滚。

详情新增闭合版本化 `integral_selection: { version: 1, give_integral: string }`。编辑器维护读取就绪与独立修改标志；旧响应缺失时禁用控制并不提交积分。普通保存先剔除版本化元数据和顶层旧版 `give_integral` 回显，再仅发送明确修改值，避免整表单回显成为写入意图。商品复制继续继承可信来源积分，复制页不发送新普通作者字段。共用 Supplier 规范化/物理包装、复制三个模块、Out 服务、架构、权限计划、支付/奖励/退款消费者、CI 和原生运行器保持原字节。

## 真实业务验收

新增测试完整追加到既有允许的 `supplier-product-recommend-image-native.test.ts`，保留 main 上原 68 项测试的全部文件字节前缀，不扩展原生运行器准入或 600 秒文件预算。最终运行完整文件；筛选预检结果不计为完整通过数。

作者测试覆盖三类履约的写入、小数读取、省略不更新列及明确清零，SELECT-only 查看者的只读回显，外租户/无权限/格式拒绝且业务与序列不变，以及具有实际正向对照的跳过、改值、延迟改归属/显示/履约类型和撤权回滚。还测试积分与推荐图、商品标签、品牌、服务保障、规格参数、留言表单、会员资格及独立佣金开关同时提交。

四个完整链路实际执行全部 185 项迁移、283 张表的隔离架构，通过既有 commissioning 和支付安装器配置独立非所有者 APP/ADMIN LOGIN，并核对双方实际权限。真实当前 App 的 Supplier、平台审核、买家 JWT 中间件参与商品创建、读取、审核、购物车、确认、订单创建、余额支付、人工发货和收货 HTTP。JWT 按本地合成账号密码版本签发，不声称覆盖公共凭据签发。卡密全链路使用固定内容模式；一次性卡密维持既有消费者合同，本批未新增其全链路，不冒称一条链路包含两种模式。

商品每件 2.75 积分，数量 3，实际订单积分快照为 8。下单后通过 Supplier HTTP 清零当前商品，既有订单仍保留 2.75 和 8 的来源；付款及支付任务完成后积分仍为 100。余额从 100.00 实际扣至 70.00，重复创建只分配一次订单号，重复支付不再扣款，支付消费重放不重复分配。三类商品均确认收货后积分从 100 变为 108，账单按实际履约订单只记一笔 8，重复收货被拒绝且不增发。全量商品退款经真实服务及 SQL 余额结算恢复至 100.00 并扣回 8 积分；另一个实物链路在收货前退款，积分一直为 100，不误扣未发奖励。重复退款保持账户及账单不变。退款申请/最终结算直接调用实际服务，不声称经退款 HTTP 或外部支付提供方。
