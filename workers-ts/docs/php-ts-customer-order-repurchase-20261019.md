# 买家订单再次购买（2026-10-19）

PC 与 UniApp 在普通订单待评价、已完成时提供“再次购买”。只发送原公开订单号 `{uni}`；服务端从买家自己的受保护商品快照取得精确 SKU 和件数，按当前商品可售状态、库存、单次限购、付费会员资格和当前预售窗口，原子地准备独立的 `isNew=1` 结算选择。返回的精确购物车 ID 进入现有 `mode=buy` 结算，不混入普通购物车、旧直接购买选择或已认领记录。此动作不创建订单、不付款、不预留库存。

响应来源必须与当前公开订单号及物理订单行一致。双击、读取刷新、页面隐藏、账号和路由变化、同一路由 A→B→A、物理行替换、迟到响应及结算导航失败均受上下文约束。导航失败保存已确认 ID，继续进入结算不重发准备请求；响应丢失或载荷不能核对时锁定当前页面意图，并可重新读取原订单。重新读取不假称找回未知的准备 ID。服务端没有新增跨整页重载、重新挂载或标签页的幂等账本，明确的独立再次准备会产生独立临时选择。

## PHP 来源与差异

实际 PHP 控制器 `StoreOrder::again` 排除活动订单类型 1–5，再按 `tidyOrder` 中 JSON 购物车活动类型 0 过滤。物理 `store_order_cart_info.type` 是平台、门店或 Supplier 来源；普通 Supplier 商品必须保留。原赠品同样按当前普通售价重新准备，不重放原赠品资格、旧优惠或旧售价。

实际 PHP 双端模板都只挂载已收货、已完成入口。UniApp 对其他已付状态计算的 `class_again=6` 没有模板消费者；不能把该未挂载标志算成已有交互。API 本身继续保留 PHP 较宽的付款/履约状态准入，不额外要求已收货。原 PHP Redis 结算缓存 ID 由现代 PostgreSQL 独立直接购买行 ID 替代，保留 `cateId` 兼容别名及原 `cartIds`。

现代接口有意收紧不可靠输入：最多 100 行、每行 JSON 最多 32KiB、物理数量为 1–32767、所有非空 SKU 别名一致，不能猜测当前首个 SKU；同商品多行单次限购按整批数量合计。PHP 对缺失 SKU 选择首规格、坏数量抬为 1，以及 new=true 逐次单行限购的容错不宣称原样兼容。来源文件 SHA 和精确行范围见机器账本。

付费会员专享资格使用会员卡总开关、有效期限或永久会员；优惠折扣开关不决定购买资格。SKU 锁先于商品锁，复用成熟会员行和配置 NOWAIT 保护，SQL 时钟在写入前后检查资格。当前预售转换复用成熟事务核心；普通/预售混合选择的后续结算限制仍由现有结算合同决定，不宣称完整混合预售下单通过。

## 尚未完成的累计限购

PHP 原逻辑按留存历史订单快照的 `cart_num − refund_num` 计算累计限购；这本身不证明完整历史覆盖或退款代际。迁移后的可授权额度仍需相应证明。目前 TS 历史读取明确返回 `incomplete`，缺激活前及已删除历史覆盖，也没有所有创建作者共同使用的并发额度扣减/取消退款释放权威。因此本批拒绝累计限购商品；拒绝不等于已完成该 PHP 能力。下一步仍须补历史激活覆盖、原订单去重和并发额度账本，不能把分配父子单重复相加或把未知历史当零。
