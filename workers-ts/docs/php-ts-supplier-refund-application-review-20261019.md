# Supplier 退款申请商品与关联订单核对

PHP Supplier 的实际退款详情挂载 formType0，商家处理申请前可核对选中商品、规格、编码、赠品、申请数量和结算参考。本批在 TS 售后详情接通这条只读流程，沿用 `supplier.refund.view`；原同意退货、拒绝、退款、备注、渠道状态与退货凭证继续使用既有作者和会话约束。

## 来源与兼容

新增闭合 `application_review`，按精确退款 ID、关联物理订单、UID、商家和门店绑定。现代 v1/v2/v3 申请冻结的是商品身份与申请数量；名称、规格、编码及结算参考来自仍与原申请精确相符的订单商品记录，申请数量绝不采用全单数量。旧 PHP 完整数组则使用实际申请作者按数量切分后保存的快照，编码按原 spec_type 选产品或 SKU，原字符串 cart ID 不经过 Number 转换。两种来源在界面分别说明。

拒绝或取消已释放数量时，只要原身份和购买数量仍可核对，申请继续可读；后续拆单移动、改量或改键使关联失效时明确不可用，不借用当前剩余单或今天的商品目录。已完成 v2/v3 物化退款仅指向既有受保护 `refundHistory` 归档；完成的 v1 缺少此归档时不伪造历史。完整 PHP 旧数组可独立展示，包括超过64KiB的完成记录，原历史 helper 的64KiB准入仍保留，避免误增归档错误。

收货、留言、付款金额和时间明确来自“关联订单记录”，没有宣称它们是申请时冻结值。申请数量下的结算单价与小计使用整数分精确计算，缺失旧零价显示未记录，有证据的真实零价保留；结算参考不代表退款到账。旧服务缺少新字段时提示重新读取，已存在但非法、错单或不完整的合同拒绝绑定详情，并可明确刷新。切换、关闭、路由、会话与 ABA 迟到响应清除旧资料。商品、规格、编码、地址和 HTML/URL 均为纯文本。

原 `cartInfo`、`orderInfo` 两个未知原始字段保留键且固定为 null；当前 TS 消费者没有依赖其内部结构。详情改为显式订单和渠道标量列，申请仅返回白名单商品和关联记录，不再带出旧磁盘内容、卡密、客户答案或完整 provider 对象。没有宣称所有 Supplier 端点的任意历史 JSON 都已审计。

## 读取与验收

全部读取沿用同一 RR/READ ONLY 事务，每条 SQL 的 statement_timeout 至多5秒，非整段事务总时限。现代 claim 在 SQL 传输前限64KiB、PHP 数组限1MiB；完整商品集合沿用200行、每行64KiB和整组8MiB检查，选中 DTO 最多100项、整体512KiB，标签每字段4096字节，cart key 最多128码点/512字节。真实 SQL 权限或缺表错误继续失败，不伪装空商品。

最终 **562项不同用例、12文件通过，101项新增**；Supplier 全类型/生产构建和 Worker 普通、运行时两个完整类型项目通过。15份执行源按相关成功阶段绑定最终字节，70份生产构建文件在完整 Browser 前后不变。命令、输入指纹、早期失败、清理和限定见[验证账本](../audit/php-ts-supplier-refund-application-review-20261019.json)。

真实作者验收包含两条注册 checkout/供应商分配链：Customer App/api JWT 的 v1 申请与取消，以及 v2 申请、拒绝、再申请和完成物化；付款准入是明确的自有合成前提，Customer SQL 是维护边界。v3 使用实际 CustomerWork quote/revision/operation receipt 作者产生申请，其原单、供应商归属和标签是已披露的合成设置，不能称第三条 checkout。Supplier 每次读取使用独立 SELECT-only LOGIN 与真实 App/JWT，核对所有公共表和序列不变。另保留成熟归档与退货凭证实际 SQL/上传签名回归。

最终 Browser 使用生产构建、真实 App/JWT 和独立只读 PG：9次业务 GET 对31表/29序列逐次零写，provider调用0。1200×844和390×844同源iframe实际核对部分申请、PHP赠品/双编码、完成归档、拒绝失联、长 HTML/URL 文本、503清空与显式重试；写按钮不可用、无可执行子元素，控制台 warn/error 采样没有未解释项。展示和完成归档夹具是合成记录，实际作者由原生用例独立证明。5座自有 PG（含失败候选）全部自动清零并独立确认停止。

早期运行均保留但不重复计数：新组件使旧 setup-only 测试的专用 loader 缺失，改为通用 Vue loader；环境缺 npm 入口后用已安装 Node 直接执行相同构建；严格类型先后发现显式数组类型、共享类型别名和夹具环境推断问题，修正后整套重验。Browser 首候选重复创建父夹具已有的退款表，仅修夹具的精确建表集合；第二候选实际页面已工作，但验收桥错误预期中文 body，实际 HTTP 客户端显示503，修正断言并完整重跑。没有用失败候选宣称最终 Browser 通过。首轮原生68/70通过，两项真实旧作者夹具因只识别一套已注册数据库而被拒；按成熟 checkoutPricingFixture 接入两套精确注册表的 OR，保留版本、URL、schema、host/port 和只读权限限制，再对完整70项和普通Worker完整类型项目重验。新文件暂存后的空白检查还发现测试末尾多一空行，仅移除最后一个换行，随后按最终字节重跑141项前端/类型/构建及普通Worker完整类型检查；原生和Browser输入保持不变。

22份真实 PHP/基线 TS 来源重新核对字节与引用范围；原88/404复选行逐字保持。保留用户选定已恢复的 PHP get_script 兼容和修订退役审计，Browser 启动实际 GET200。分支 `codex/supplier-refund-application-review`，草稿 PR 基于 PR119，实际提交/远端和准确新提交 CI 以发布回执为准；整体迁移继续 active。外部浏览器扩展连接、真实设备、生产部署/角色和 provider 验收仍开放。
