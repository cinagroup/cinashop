## 原始版本已核实的代码边界

- `LegacyOrderCompatibilityService.rememberCheckout` 仅存 `{cartIds}`；`checkoutPreview` 的 computed 复用原 key，不保存每次展示的报价版本。
- `OrderController.orderCreate` 在请求显式包含 cartIds 时直接解析，不读取确认缓存。服务端仍校验用户和购物车所有权，但不能据此证明该购物车已被当前 key 确认。
- `StoreOrderCreateService` 创建时重新计价；事务内首单资格/积分可再次调整最终金额。只在控制器重新报价一次并比较，仍不能保证实际落库金额与确认一致。
- `view/common/checkoutQuote.ts` 的 fingerprint、PC 的冻结 payload、UniApp 的提交 journal 都是前端状态保护，不是服务端可信报价证明。
- 两端目前只对精确 `ORDER_FORM_REJECTED` 开放明确未建单后的编辑恢复。直接增加通用报价拒绝会使用户被当作“结果未知”锁住；必须配套明确错误合同与结果核验。
- `AdminAssistedOrderService` 已校验操作者/游客/购物车快照，但快照同样不含报价、地址或运费版本。本轮仅源码核实此点，尚未执行其跨请求变化探针，不能把用户端 8 项证据外推为代客已验。

## 完成此项的必要合同

1. 服务端签发可校验的、带有效期和版本的确认凭据，绑定用户/操作者、幂等 key、精确购物车与数量/SKU/活动、地址内容、配送/门店、优惠选项和规则版本。金额按整数分、积分按整数绑定，不能接受客户端自报金额作为权威。
2. 区分稳定的建单幂等 key 与不可变的报价版本；同一结算页改地址、多个页面或乱序 computed 不能覆盖另一响应所指向的确认。若使用 KV，不假设跨地域读取立即一致，不用最后一次可见写入冒充用户收到的版本；存储方案须按实际一致性保证设计，不能只增加客户端比较。
3. 普通、活动、套餐和代客实际入口统一接入；显式 cartIds、无缓存、旧版本或未知 key 不得绕过。允许合法的无地址预览、虚拟免物流和独立自提联系人。
4. 创建事务在真实最终金额确定后、提交前校验确认，变化则整笔回滚；不能只比较创建请求早期金额。保留现有地区/运费/库存守卫，不为跨请求合同长期持有数据库锁。
5. 未建单且明确需要重新确认时返回可识别的 `ORDER_QUOTE_RECONFIRM_REQUIRED` 与精确 orderKey；PC/UniApp 可显式获取新报价，但不能静默改价或自动付款。曾发生超时/未知结果的提交先核验原结果，不能仅凭后续一次拒绝清除旧意图或换 key。
6. 已存在的同所有者订单优先幂等返回；确认过期、地址删除、规则失效不能让重放创建第二单。另补跨账号、过期、篡改、支付入口未触发、失败回滚、多连接竞争与两端浏览器测试。

砍价原参与应锁快照还是跟随活动现价，仍由 A3i 的产品决定约束。本项可以拒绝未确认的新报价，**不能趁机改动价格公式**。A3k11d 的全局配置 SQL 权威/缓存一致性仍是独立缺口，签发凭据本身不解决陈旧配置读。
