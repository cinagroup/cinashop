# Historical Routine payment accounts

Implementation scope: explicit owner-authenticated maintenance journal, a closed secret registry, exact default-query selection and a dedicated approved-account callback. This is not historical login ownership, a configuration switch permit or production commissioning evidence.

Two optional tables are installed together by runRoutinePaymentAccountPolicyUpgrade on actual owned PG16 maintenance LOGIN and exact full runtime declarations. No policy or query selection is automatically adopted from current config. App can SELECT policy; App can SELECT/INSERT use. Other runtime roles get no new grants. The original provider/evidence v1 schemas and canonical hashes remain unchanged.

Registry binding: ROUTINE_PAYMENT_ACCOUNT_CREDENTIALS is one bounded secret JSON document with exact {format:1,credentials:[...]}. Every entry has exactly ref, version, appId, merchantId, serialNo, apiV3Key, privateKey, platformPublicKey, platformPublicKeyId. At most16 entries, max512KiB document; each PEM max8192chars; APIv3 key exactly32 UTF8 bytes. (ref,version) is unique. References are opaque handles in this closed deployment-provisioned set, never arbitrary paths, environment variable names, URLs or user secret-store selectors. AppID/merchant and every material byte participate in an APP_KEY-keyed independent-domain commitment. No current/KV credential fallback. No credential, key or access-token secrets enter journal, sidecar, public DTO or Queue. The internal App-restricted sidecar does contain authenticated provider facts, including payer/openid; it is not an anonymous public receipt.

An operator obtains routinePaymentCredentialCommitment for an explicitly selected archive bundle, reviews actual provenance/organization permission independently, then calls appendRoutinePaymentAccountPolicy with that public pair/ref/version/stamp, purpose query and/or notify, active/revoked, validFrom/Until (positive seconds; interval max366days), operation UUIDv4 and expectedRevision. The actual maintenance database/name/OID/backend are authenticated; immutable payload binds exact database and maintenance OIDs. Every subject history is complete/bounded64 revisions and authenticated as a chain, else refuse. New revisions use a global independent exclusive gate. Retrying the exact operation recovers its existing receipt without requiring withdrawn credential materials. A registry entry alone is not approval; an approval is not payment evidence.

Query plans are separate journal subjects, keyed by an opaque HMAC of provider/profile/orderNo and explicitly bind concrete domain, amount, CNY, accountId/accountRevision, active state and time window. The latest account revision must match. Missing plan preserves current-account query compatibility; a present revoked/invalid/expired/mismatched plan never falls back to an earlier plan or current credentials. Unknown domain and same-number cross-domain substitutions refuse exact plan matching. No credential enumeration or automatic history guessing.

Callbacks use POST /api/pay/notify/routine-account/:accountId under the production /api mount. The opaque route segment only chooses one approved notify verifier. Headers/body do not approve anything. Real RSA/serial checking and AES-GCM execute with that exact bundle; decrypted AppID and merchant must equal policy. Current legacy callback routes retain their current-account checks; adding a historical approval does not relax them.

Provider HTTP and RSA/AES verification stay outside SQL transactions; local HMAC validation and material commitment may execute inside short SQL transactions. Short App transactions check policy before/after HTTP/verification. Fresh capture takes the shared account gate before original physical-order/provider/event boundaries. Original evidence, signed account-use provenance and callback event/outbox commit together; query capture binds the exact server claim. Tail checks enforce active SQL-clock windows and a5s SQL transaction deadline. The sidecar binds its first original evidence signature and the actual observed provider facts/response digest, exact approval and optional query plan. Local domain/amount mismatches can retain genuine observations with scopeMatches=false, but cannot settle. Replay of the same evidence/account-record/query-record key retains its first sidecar and the original rows/xmin. A distinct approved revision can append another immutable use for the same original, without rewriting existing records.

Accepted evidence remains a fact after account retirement/revocation. Settlement holds the order and reads durable provenance without acquiring the account gate backwards; it verifies the immutable historical journal records and original binding rather than requiring current credentials or current approval. Existing v1/current-verifier evidence can have no sidecar; that absence grants no historical account selector. This is not a claim that all legacy rows have complete account-use classification.

Still required for full migration: operational credential provisioning and real account approvals; historical refunds, shipping and notification tokens; comprehensive internal/external object classification and manifest; atomic switch permit consumption and all consumers; frontend journals/DTO/session/Browser and inherited CI failures. Preserve all existing users, rights, UIDs, old orders/payments and unresolved history. AppID first adoption/material-switch barriers remain closed.
