# 个人中心商家经营与订单管理验证（2026-10-03，本地部分候选，未发布）

本批承接个人中心经营统计和商家订单入口。客户端新增经营统计、订单列表、订单详情、发货、退款、物流六个真实页面；后台另设用户 JWT、当前有效店长和明确门店范围的 `/api/store/manager/*` 合同。它们属于本地未发布候选，不能据此关闭整个用户中心、UniApp 或生产验收父项。

## 路由和身份合同

旧移动商家接口位于 PHP `route/api.php` 的 `admin/order` 分组。旧客户端实际使用的经营统计、订单列表/详情、发货、拆单、改价、线下收款、主动退款、售后审核和物流均须逐项对照；现有 Worker `/api/admin/order/*` 属于后台管理员合同，不接受普通用户 JWT。新实现从实际用户、门店、店员三份 SQL 权威确认当前账号、唯一有效管理身份和当前门店，不借用顾客或管理员身份。

多个有效管理门店须明确选择，不能默认第一家。重复门店身份、撤权、停用账号、停用门店或范围版本改变后，旧订单响应和表单不得继续展示或提交。个人中心旧待发货指标的 `pid IN (0,-1)` 保持；经营订单统计采用旧 DAO `pid=0` 的实际语义 `pid>=0`，包含履约子单，排除支付父单。旧数值筛选器按 DAO 谓词实现，不能把筛选器直接当原始订单状态。

列表计数与数据、经营趋势、详情和配置在只读一致性快照内读取。商品访问只计当前门店商品，并明确标记门店口径。分页、日期范围、搜索字段和数量均有界；跨店订单、重复业务号、顾客归属错误的商品快照和未经归属验证的退款图片不能混入公开投影。

## 写入和恢复合同

备注、手工快递、实际本店配送员和整单虚拟交付，复用已有履约事务和持久通知。拆单发货保持金额、数量、顾客和门店归属，提交与原请求回执原子落库。虚拟商品沿既有商品类型政策，禁止把自动卡密、次卡或到店核销混入手工发货。

原请求固定为版本、门店、范围指纹、订单 ID、订单版本和完整 payload 六个字段，配合账号隔离的 UUID。服务端在异步读取之前冻结原始 JSON；金额和文本的内部校验不能替换被哈希的原始意图。同一 UUID 只能重放相同内容；先保存的成功、已受理或放弃回执不能被后续拒绝覆盖。未知 SQL、网络或提交结果不产生“未执行”证明；回执缺失、404 或时间经过也不能解除原意图。

实际订单资源锁先于用户和管理角色锁。普通数据库 LOGIN 沿既有业务权限运行，台账仅 SELECT/INSERT。新独立 NOLOGIN 协议只为店员表、快递公司表加固定范围的锁；运行时检查真实函数、对象、所有者、权限及源定义，不在请求中安装、授权或修复。用户和门店锁使用原有权限。

旧虚拟发货页面是 500 字符文本框，允许多行。新输入保留备注和虚拟内容的换行、回车与制表符，拒绝 NUL 和其它控制字符；物流编号仍为单行。已有履约核心的状态日志列仅 256 字符，本批只对状态描述截断，实际订单的虚拟交付内容完整保留。POST 在解析前限制 UTF-8 JSON 容量和编码。

财务操作分别核对改价、真实线下收款、申请创建和资金执行。退款申请不等于退款完成，外部渠道受理不等于资金到账。主动退款复用成熟实体拆单协议：申请阶段只预留原购物车数量；真实资金、库存回退和最终事务完成后才物化两个子单。原订单成为 `pid=-1`，退款/支付凭据仍绑定原订单，子单详情按持久拆单记录、指纹和实际分区读取，不能改写退款归属来拼出展示结果。

原 UUID 的只读资金状态查询固定返回 `merchant-order-operation-v1`。角色撤销后，原已认证账号仍可读取自己的最小回执和资金结果；其它账号不能读取。只有原不可变渠道受理证据、真实退款成功及已要求的实体物化一致，才显示已完成。客户端保留原 UUID/body，渠道受理后不创建新退款意图、不自动重发，不把申请创建或 `PROCESSING` 当作到账。真实提供商外部 HTTP 未在本批验收。
