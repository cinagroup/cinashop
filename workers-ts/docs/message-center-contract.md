# Customer message center and consuming inbox contract

This slice uses immutable PHP commit `8ed2a5b139f9170dd11b0dff91803f2fd59e40a5`: `app/controller/api/v1/user/SystemMessage.php`, `app/services/message/SystemMessageServices.php`, `app/dao/message/SystemMessageDao.php`, `app/model/message/SystemMessage.php`, `app/services/message/service/StoreServiceRecordServices.php`, `app/common.php::time_tran`, and `view/uniapp/pages/users/message_center/{index,messageDetail}.vue`. The summary and paginated inbox are distinct operations. Reading the inbox by GET intentionally consumes the caller's read state, as PHP does.

## Transport and visibility

All three existing routes require the current registered-user JWT, match the persisted password version, reject disabled/deleted accounts, and respond `Cache-Control: private, no-store`, including authentication failures. No query UID selects authority. Optional query keys must be unique, exact, and canonical: summary/list allow only `view,page,limit`; detail allows only `view`. Page is 1..1000 and limit is 1..100 (default20); detail ID is a canonical positive int4. Database/validation/capability failures propagate; they never become a successful empty list.

Visible system messages have `status=1,is_del=0,type IN(0,1),user_id IN(0,currentUID)` and sort by `add_time DESC,id DESC`. Staff type2 and all other audiences remain isolated. `system_message.look=1` is retained as imported already-read evidence. Otherwise a matching `user_message(uid,message_id,is_read=1)` establishes read state. Global message rows are never updated by reading.

Default `GET /api/user/message` returns the PHP `{system,service}` envelope. `system` is the latest visible `{id,title,content,add_time,message_num}`, or `[]`; `add_time` follows the literal PHP relative-time units (null at exactly now). `service` reuses `KefuRealtimeService.userConversationList`, including legacy `_update_time` and misspelled `mssage_num`; avatar previews are authorized separately from stored identity.

`GET /api/user/message?view=message_center` returns exactly:

```
{owner_uid,query:{page,limit},system:null|{id,title,content,add_time,message_num},
 service:[{id,to_uid,nickname,avatar_source,avatar,update_time,message_type,message,mssage_num,online}],
 service_count,page_count}
```

The service count comes from the full caller-owned non-tourist conversation relation, not the current page length. `page_count=ceil(service_count/limit)`. Modern times are nonnegative integer epoch seconds. Service message types are1..7, retaining the existing legal refund-message type7 (shown as a refund summary instead of rejecting the whole page). Canonical avatar identity and signed preview are distinct; unresolvable/unsafe values produce blank fallback. Signing does not fetch R2 objects or send provider messages. Summary reads use one repeatable-read/read-only transaction.

Default `GET /api/user/message_system/list` returns `{list,count,service_num}`; an empty page retains PHP's exact `{list:[],count:0}`. Rows contain `id,title,content,look,add_time`, with relative legacy time. `service_num` is the unread count BEFORE consuming this page. The opt-in `?view=system_messages` returns exactly `{owner_uid,query:{page,limit},list:[{id,title,content,add_time}],count,page_count,service_num}` with true full count and total pages, including when the requested page is empty.

Modern `GET /api/user/message_system/detail/:id?view=system_message_detail` returns exactly `{owner_uid,id,message:null|{id,title,content,add_time},service_num}`. A hidden/foreign/missing message returns null and changes nothing; a visible detail consumes only that ID and returns the unread count AFTER consumption. The default detail remains nullable with legacy relative `add_time`. Neither route interprets content as HTML. Complete response bytes are bounded to1MiB; title/content and service fields fail closed on invalid or excessive text rather than truncating system-message contents.

## Versioned receipt capability

`src/migrations/userMessageReadCapability.ts` exports the explicit maintenance installer `installUserMessageReadCapability(db,{app,admin,maintenance,owner})` and existing-transaction component. The separately provisioned `owner` must be a fresh restricted NOLOGIN identity with no surviving authenticated session. Both installation and ordinary inspection reject any `pg_stat_activity` row for that owner OID; switching LOGIN to NOLOGIN does not revoke an existing connection. Installation requires the actual PG16 superuser maintenance LOGIN, ordinary origin/RC/RW transaction, supported catalog, bounded timeouts, no event triggers, and distinct identities. It does not create roles, repair drift, change shared baseline grants, or run during startup/HTTP. The existing full runtime business audit admits only the exact reviewed function OID for App; Admin receives no execution right. Absence remains valid for unrelated shop routes; consuming inbox reads return503 until explicitly installed.

`public.cinashop_user_message_read_v1(integer,integer[])` is SECURITY DEFINER with fixed `search_path=pg_catalog,pg_temp`, fully qualified relations and no dynamic SQL. PUBLIC execution is revoked; App receives only EXECUTE on this addon. App retains its existing SELECT-only access to `user_message` and receives no receipt-table/column DML or serial privilege. The function owner has only SELECT on user/system_message/user_message, INSERT on user_message, UPDATE(is_read) on user_message, and USAGE on its canonical int4 serial. Catalog review pins exact body/signature/flags/ACL, owner identities and all table/column/sequence privileges, ordinary relations, defaults, indexes/constraints and serial parameters. Existing checkout/pricing definer OIDs are independently audited and are not substituted for this capability.

The controller creates the actor solely from authenticated middleware state. The service locks/rechecks that account's exact persisted credential version using the already-reviewed App user-table authority. Read/write transactions take a per-UID advisory lock before observing receipts. The complete page, full count and pre-unread value use ONE materialized SQL statement snapshot. READ COMMITTED is intentional: a reader that waits for the UID lock must observe the preceding reader's committed receipts; REPEATABLE READ could retain an older snapshot and allocate duplicates on this historically nonunique receipt relation. The capability rechecks current account context and visible IDs before writes. The page statement is a reading observation point; no claim is made that maintenance cannot subsequently hide a message.

Within that fixed UID lock, any existing read1 receipt or imported look1 means zero changes. If only old read0 rows exist, all those rows change only `is_read` to1, preserving IDs/timestamps and allocating no serial. If no receipt exists, insert a single current-UID read1 receipt with bounded server seconds. Absence is checked BEFORE invoking the serial default; replay does not rely on an INSERT/ON CONFLICT attempt that wastes serial values. The complete input array is validated before any insert. The runtime result has exactly read_ids/inserted_receipt_ids/updated_receipt_ids and is validated against the requested sorted IDs.

The App SQL LOGIN is trusted shared application authority. Transaction-local UID/password context is supplied by the trusted service after JWT/account validation; it is not independent JWT verification or per-tenant RLS against a compromised App role able to issue arbitrary SQL. This explicit boundary also applies to the existing full-shop App profile. No maintenance connection is used for business reads or consumption.

## Customer-service boundary and acceptance

Explicit `to_uid>0` history selection now refuses missing/disabled staff rather than silently returning a different online agent. Explicit valid offline staff remain selectable; only default0 may choose automatically. History avatars are resolved against the selected persisted service UID and attachment metadata, then signed with the same900-second policy as the center. Signing fetches no R2 bytes; unsigned canonical paths remain forbidden. History selection is a read: it does not reset `store_service_log.type` or `store_service_record.mssage_num`. Later realtime socket `to_chat` handling is separate and may write read state. No provider send or production realtime availability is implied by summary/history acceptance.
