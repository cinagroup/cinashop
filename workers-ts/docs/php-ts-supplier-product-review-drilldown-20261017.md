# Supplier 商品评价钻取与回复

旧 Supplier 商品列表的 `reply(id)` 进入 `/supplier/product/product_reply?id=<商品ID>`；评价页读取该商品与 `is_reply=0`，支持查询、分页、回复和修改回复。本批将这一完整消费流程接到 TS：商品列表的“查看评价”进入 `/product-reviews?product_id=...`，页面明确显示当前商品编号，并可返回全店评价或商品列表。

页面也接受旧 `id` 参数及 `is_reply=0|1`。商品选择必须是单个正整数，不能同时带两种商品参数；空值、重复、越界、非规范数字和未知路由参数不会悄悄回退到全店查询。全店入口仍使用无商品选择的原 GET。商品名、用户名称、回复状态与分页始终携带当前商品过滤；商品变化会重置筛选和页码。待回复列表最后一页在回复后变空，会按重新读取的总数回退到有效页。

实际接口仍为 `GET /supplierapi/product/reply` 与 `PUT /supplierapi/product/reply/set_reply/:id`。原 `content` 正文兼容，新页面另传可选的正整数 `expected_product_id`，服务在最终锁定评价后核对当前商品。这是商品绑定，不是版本 CAS；不增加数据库迁移、操作账本或删除评价能力。

GET 在 REPEATABLE READ／READ ONLY 事务内读取评价、总数与官方回复，核对实际 JWT 对应的当前账号、口令版本、有效期、供应商和查看权限。运行连接须为已有普通非特权 LOGIN，具备 auth 四表及 product／reply／comment 七表 SELECT。本店评价与本店商品的 type=2、relation_id 必须同时成立；平台、其他店铺、已删除评价及两侧归属冲突均不进入本店结果。官方回复只选择同一供应商、uid=0、pid=0且未删除的 comment，不借用平台、其他供应商或用户跟评。

HTTP 回复复用现有 Supplier 实时授权校验，并在实际 auth 行 SHARE NOWAIT 栅栏内持有账号、供应商、角色及相关菜单。沿用既有评价写入的商品优先锁序，再锁评价并复验商品、身份、权限与有效期。缺少管理能力、口令或账号变化、等待期间评价改属另一商品、真实锁冲突均失败关闭。仅新增／修改当前供应商的官方 comment 和评价 `is_reply`；原评价内容、客户、评分、商品评分、SKU、库存及资金哨兵保持不变。普通运行权限计划已具备所需授权，本批不修改生产 profiles 或执行生产 GRANT。

前端使用真实 Pinia 会话与 Axios 取消信号。商品、筛选、页码、路由、权限、卸载及跨窗口会话 A→B→A 会清空旧列表和回复草稿，取消排队或在途请求；迟到结果不能重新打开旧弹窗，也不能向新商品回填。回复在发送前重新核对当前列表目标、权限和商品编号；提交中阻止重复点击。成功回复后读取当前筛选，未知结果仅提示手动查询核对，不自动重发 PUT。正常回复与修改使用同一既有接口，原评价不允许被供应商删除。

验收覆盖实际渲染 SFC／Pinia／Axios、独立受限 PostgreSQL 16 LOGIN 与实际 App／JWT，以及生产构建在内置浏览器中的商品入口、待回复筛选、一次新增和一次修改、本店另一商品、只读账号和跨窗口迟到回复取消。浏览器仅使用本机合成数据，不发送真实客户消息或调用第三方 provider。精确通过数、失败历史、源指纹、夹具清理与 GitHub 推送见本批审计；整体 PHP→TS 迁移保持 active。
