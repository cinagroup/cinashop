# Out 库存同步的条码候选边界

2026-09-10，工作区候选。历史 PHP 数据复制／对账按所有者决定不适用；以下是本机专用 PostgreSQL 16.15 的合成业务验证，不是生产 Hyperdrive 或完整迁移验收。

## 已复现问题

输入最多100条并不代表查询结果有界：一个条码对应400个合法SKU时，原发现查询实际返回400行；100个条码各重复10次时实际返回1000行。原业务已经拒绝歧义并保持数据不变，但先把所有候选带回Worker，仍有内存及后续锁集合风险。两项红测均精确失败于真实驱动返回行数，未用伪造SQL结果代替数据库。

第一版以每个条码LATERAL LIMIT 2限制结果，相关7项通过；再用真实执行计划发现该夹具下SKU Index Scan执行100次，因此未保留该版本。执行计划红测2通过／1失败；改为单个过滤集合的窗口排名后3项通过。各阶段不累加，也不把扫描次数当作耗时基准。

## 当前合同

- 参数化过滤请求条码及原有合法范围：平台type=0、relation_id=0、实物product_type=0、商品未删除、普通且未退役SKU。实物条件从原后续复核提前，防止低ID的非目标行占满限额；后续商品复核仍保留。
- 对合法集合按条码分组、SKU ID排名，仅返回每组前两行。因此发现查询最多返回200行；两行已经证明歧义，不需要收集完整重复集合。
- 缺失／重复在取SKU锁前整批拒绝。只有全部条码初始唯一才进入原有排序NOWAIT锁和复核，最多100个SKU；不会在截断的歧义集合中猜选一个商品。
- 既有账户／全局身份建议锁、绝对库存同步、sumStock正增量、销量、库存记录及重放账本不变。隐藏／未审核的合法实物商品仍允许同步，没有新增上架或审核政策。

窗口排名可能扫描／排序大量数据库行；本次只证明传回Worker的行数有界，并排除所测100条码夹具的逐码重复扫描，不承诺数据库工作量恒定、所有数据分布均为单扫描或固定延迟。没有新增业务索引，也未执行生产迁移DDL。
