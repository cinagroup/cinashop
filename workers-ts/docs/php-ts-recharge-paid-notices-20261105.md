# Recharge buyer notices

This change supplies the buyer notice after the first verified external recharge settlement. The fixed local PHP input is `8ed2a5b139f9170dd11b0dff91803f2fd59e40a5`: `UserRechargeServices::rechargeSuccess` emits `user.recharge`, whose registered Recharge listener calls `NoticeService` with `recharge_success`.

The notification body records principal, gift, credited amount, the actual inserted `user_bill` ID and its post-balance. The source HMAC binds database/owner scope, the paid `user_recharge`, that unique `recharge_external_payment` bill, and the actual callback or signed-query record. A later wallet movement is irrelevant. A writable bill by itself is not provider authority. Already-paid historical rows, callback replay and commission-to-wallet do not create a new source or notice.

0202 is an explicit PG16 direct-owner successor of the exact installed membership/domain-subject predecessor. It adds the paired `recharge.settled` and `recharge.pay.success.notice` events and a separate recharge delivery subject. It grants no roles and performs no business adoption. Known inactive predecessors remain silent; unknown/partial catalog states fail closed. Existing 0200/0201 artifacts retain their bytes. Old addon wrappers preserve the recharge tail and independent addon choices, including comments, rows and replay OIDs.

The buyer mark is `recharge_success`. SMS receives `price` and `now_money`; inbox receives `order_id`, `price`, `now_money`. Official template42934 receives `time11` from recharge creation time and `amount5` principal, with no explicit URL. Mini755 receives `character_string1`, `amount3`, `amount4`, `date5` and the historical bill-page link `/pages/users/user_bill/index?type=2`. Dates are the fixed PHP +08:00 seconds format. Mini date5 is the captured notice occurrence, not delayed retry time.

Mini format9 uses a real original WeChat recharge payment and independently approved755 account/template/token, or an Ali payment with one explicit active UID owner and no unmapped live binding. It never adopts the current AppID or uses membership/store-order IDs as recharge authority. Missing ownership is frozen unavailable; later maintenance does not adopt the old request. Fresh dispatch rechecks source and current independent approval before its immutable attempt. UNKNOWN preserves a possible POST and never repeats it. Only proven pre-attempt transient SQL failures can schedule a safe retry with zero new attempt/result/POST.

Settlement source and pending notice are inserted in the same transaction as wallet, paid state and bill. A failed insert, returned-payload corruption or SQL error rolls them all back. Queue acceleration happens after commit and cannot roll back finance; durable scanners recover it. SMS/official configuration and skip metadata remain immutable after staging. A known long inbox title records a gap while preserving channel staging.

The new pure/history/native/catalog suites are authored acceptance, not independent review. Native cases use the actual UserJWT recharge creation route, verified RSA/AES callback, default signed query and RSA2 Ali ingress, five published LOGINs, real ownership maintenance and independent subscription approval, with controlled external transport. They cover gifting, delayed wallet changes, no historical backfill, all-or-nothing source/notice failures, lock recovery, unknown sends, ownership ambiguity and domain/bill tampering. No validation result is claimed by this document; raw frozen run evidence determines acceptance. Recharge refund `now_money` ambiguity is outside this change. The old PHP repository remains local and is not uploaded.
