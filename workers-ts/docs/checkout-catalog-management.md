## 已复现的真实问题

完整 ORM 生成的独立 PostgreSQL 16 数据库中，实际后台商品保存先取得商品主行，再等待分类；实际下单先扣 SKU，再等待该商品。释放分类后，后台保存去锁 SKU，产生真实的商品／SKU反向等待。2026-09-10 05:01:33.742 UTC，服务器记录 `deadlock detected`，买方 PID 11880 等待编辑者 PID 12492，编辑者反向等待买方；首轮红测失败。不是只凭代码顺序或计时推断。

## 修复合同

`replaceProductSkuEditor` 的两个实际调用者——后台关联编辑和供应商编辑——调用它时均已持有商品主行。该函数仍按 SKU ID 有序取锁，但改用 `FOR UPDATE NOWAIT`，不在这里等待已被库存事务持有的行。只有嵌套 SQLSTATE `55P03` 转换为“商品库存正在变化，请刷新商品后重试”；其它错误，包括死锁 `40P01`、语句取消和连接失败，原样抛出。函数没有捕获异常后继续写入，也没有自动重放旧库存输入。

异常向外传播，使原编辑事务已做的商品、关联、描述等写入一起回滚。管理员明确刷新库存后可以重新提交。没有改下单扣库存顺序／WHERE守卫、金额政策、SKU身份和库存计算；没有扩大权限或修改平台绑定。本修复只针对上述行锁反向等待，不声称消除了所有目录DDL、其它写入入口或跨商品组合的死锁。
