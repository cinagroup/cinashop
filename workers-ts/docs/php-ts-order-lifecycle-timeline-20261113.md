# 订单生命周期时间线迁移（2026-11-13）

本批补齐买家 `/api/order/detail/:uni` 和企业微信 `/api/work/order/info/:id` 的 `order_log`，并在两个现有 UniApp 详情页展示事件日期与显式刷新入口。同城 `/api/delivery_order/detail/:id` 使用同一读取器，保留自己的响应结构；本批没有新增同城配送追踪页面。

## PHP 对照与边界

固定 PHP 引用 `8ed2a5b139f9170dd11b0dff91803f2fd59e40a5`，4 个直接依据文件逐字节核对。普通记录包含 create/pay/delivery/take/complete；缺失事件返回空字符串，不使用订单头付款、创建或完成状态推算日期。发货事件优先级为 delivery、delivery_goods、delivery_fictitious，存在性包含零及负时间戳。日期使用 Asia/Shanghai 的历史时区规则。

同城记录按精确原始 change_type 聚合，保留包含 city_delivery 的匹配方式与未知标签“配送中”。PHP 未规定重复类型的排序；本批明确选择 change_time、id 最大的一条，并按被选记录的 time/id 升序输出。只下载类型、时间、ID，不暴露原始消息。普通记录最多 7 个已知类型；同城最多 10000 个相关不同类型，超限明确失败。

买家沿用现有归属和双删除过滤；企业微信保留成员/客户上下文、门店、父子单及退款过滤，同城沿用 PHP 的 uid/is_del 可见性。每个订单只读取自己的物理 oid，拆单记录不会冒充创建、付款或发货记录。

三个读取路径使用只读 repeatable-read 数据快照和不扩大既有超时的 5 秒上限。企业微信授权继续使用现有成员/客户围栏，在快照外前后验证，避免已完成撤权被快照遮蔽。详情响应在认证前声明禁止缓存。

客户端严格校验必需的日期字段和 Gregorian 日期；缺失或异常记录导致本次详情读取失败并清除旧私有视图。共享时间线只显示已记录日期，刷新重新读取真实详情。
