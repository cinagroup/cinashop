# Out 商品管理与下单并发

2026-09-10，工作区候选；历史 PHP 数据对账按所有者决定不适用。这里是完整 ORM／本机专用 PostgreSQL 的合成业务测试，不是生产权限、Hyperdrive 或发布验收。

## 实际缺口

三个实际 Hono／Out 控制器／服务与实际下单事务，经四个稳定独立 PG 后端复现：

| 入口 | PG UTC 时间 | 等待环／死锁受害者 |
| --- | --- | --- |
| 上下架 | 06:35:12.355 | 编辑 10716 持商品等买方 15068 的购物车，买方等编辑商品；编辑被中止 |
| 商品编辑 | 06:35:17.517 | 编辑 11468 持 SKU 等买方 14472 的购物车，买方等编辑 SKU；买方被中止 |
| 跨商品库存同步 | 06:35:22.569 | 编辑 10900 持商品 70 等买方 15484 的商品 71，买方等商品 70；编辑被中止 |

都有服务器 `deadlock detected` 和实际 SQL/PID 证据。库存同步测试特意更新买方未选中的额外 SKU，仍通过共享商品行形成死锁；不是只有更新同一个 SKU 才会争用。先核验真实 DAO 返回顺序，再通过 `pg_blocking_pids` 验证具体等待，不用固定延时推测已取锁。

另一个行级反例：一个活跃 SKU 同步到 9 件，另一个退役 SKU 留有 99 件，原查询得到商品库存 108；退役行不应计入活跃库存汇总。

## 改动合同

`OutProductService` 保留原重放账本、账户建议锁、全局 SKU 身份建议锁和分类表锁顺序；既有 SKU／商品查询改为 `FOR UPDATE NOWAIT`。在持有先前商品、SKU 或全局锁后遇到忙行，立即抛出刷新重试错误并退出原事务，而不是继续加入下单等待环。只将这些显式锁语句的嵌套55P03转为“商品或购物车正在变化，请刷新后重试”；其它错误不改成库存忙。

保存和上下架的购物车更新通过同一条 MATERIALIZED CTE，按 ID 以 NOWAIT 锁定候选，再仅更新该候选集合。不 SKIP LOCKED，不在 Worker 收集不限量购物车 ID。保留 Out 原有“该商品所有购物车”的条件，包括已支付／已删除行；没有擅自改成移动管理接口的不同过滤政策。Out 上下架原有所有类型商品关系联动同样保持。

库存同步总量查询补充 `is_retired=0`；退役记录本身不修改。原 stock 绝对同步、sumStock 仅随正增量增加、销量保留、库存差额审计、平台／实物作用域、条码歧义拒绝及请求归一化不变。商品保存仍保留原库存／SKU 身份／销量，不自动重放陈旧库存值，不重新安排下单取锁或放宽 SQL 时限。

## 验证层次

新测试文件 `checkout-out-product-concurrency.test.ts` 共17项：三类真实死锁；保存／上下架忙后一个购物车时完整回滚及旧键可重用；保存／同步忙后一个 SKU 时先取得的 SKU 与两类建议锁释放；创建／保存／上下架／同步的末端重放账本失败完整回滚；实际下单后保存库存／销量及同步增量／重放；Out 原有购物车／关系范围及上架清除定时下架；独立连接同键创建只提交一件商品／一个账本；非锁选择错误保留；退役 SKU 排除。

重放并发创建用真实分类表锁暂停第一个请求，验证第二个请求确实等待第一个账户建议锁；不是把串行请求当并发。新建测试仅推进专用随机库中的两条显式种子序列。回滚核对业务行，PostgreSQL 序列分配不承诺回滚。正式鉴权、KV、取号绑定均未在此证明，只有控制器之后的业务／SQL是真实路径。
