## 修复与兼容范围

`POST /api/admin/product/update_attrs/:id` 原先直接 `c.req.json()`，业务层的 500 行限制发生在完整请求解析之后。三个真实 Request／Hono 控制器红测均得到成功信封：声明超限、没有 Content-Length、伪造小长度头，都能把超大但合法的 JSON 交给服务。

控制器现复用 `readBoundedJsonObject(c.req.raw, 128 * 1024)`，先按实际流式字节数限制，再解析、调用服务。声明长度超过上限可提前拒绝；缺失或伪造长度不能绕过实际计数。超过上限时取消正在读取的流，不继续读取后续尾块。不修改共享读取器、数据库事务、500 行业务上限、库存／价格／销量／归属和锁策略。

128 KiB 是包含 JSON 语法、空白和未知字段在内的请求总字节上限。测试覆盖 500 行五个已定义更新字段、8 字符 Unicode 标识、各字段最大值以及四空格格式化／Unicode 转义编码；这些输入超过 64 KiB，仍小于 128 KiB。不是任意冗余字段或任意空白都保证接受。单元测试的最大单行库存只证明字段解析能力，实际业务仍独立限制总库存，未放宽这一规则。

成功仍返回 `{status:200,msg:"修改成功",data:{changed}}`，超限是 PHP 兼容的 HTTP 200／业务 status 400，保留 private no-store。空主体／JSON null 经已有读取器规范化为空对象后仍拒绝，提示为“请填写属性值”；非对象／畸形 JSON 在服务之前拒绝。底层输入流错误继续抛出，不伪装成已成功修改。
