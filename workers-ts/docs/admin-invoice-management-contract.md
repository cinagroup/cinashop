# Admin 发票申请管理合同（2026-09-28 本地候选）

旧 `/admin/order/invoice/list` 是已付款、未删除申请的管理页：按申请时间、状态、订单/用户/抬头查询，查看个人或企业抬头，填写开票状态、号码、备注并导出当前页。旧服务的 `invoice_id` 是模板 ID，列表别名 `invoice_id` 却是申请行主键；`id` 是订单数据库主键，`order_id` 是公开订单号。新实现保持这些身份分离，管理操作只接受申请行 ID，页面显示公开订单号。旧 `makeUp` 创建申请时留下 `invoice_amount=0.00`，因此旧后台允许手填金额；本实现拒绝客户端金额，只在权威证据允许时由服务端补齐。

新 Admin 页为 `/order/invoice`，API 在 `/adminapi/order/invoices` 与 `/api/admin/order/invoices` 双前缀各注册列表、详情、完整订单信息和处理。列表默认每页10条，上海时间精确到分钟且结束分钟包含；支持待开票、已开票、已拒绝、已退款及订单号、UID、订单姓名/电话、抬头、开票电话查询。列表与详情使用有界、只读、可重复读快照；孤儿、错属、已删、退款中、金额或历史异常按行展示诊断，不因一行坏数据隐藏整页。详情展示开票资料、订单摘要、保存金额与证据推导金额；当前页 CSV 沿用旧八列顺序，并中和可能作为公式执行的文本。

`GET /order/invoices/:id/order-info` 仅接受发票申请行 ID，并单独要求 `invoice.view`；两个前缀规则相同。它在只读、可重复读快照内重新核对申请已付款、类别、UID、来源订单、拆单支付主单及活跃申请唯一性，不扩宽通用 `order/detail` 的 `order.view` 权限。成功的 `data` 仅返回 `{ invoice_id, order, user, cart_items }`：`order` 是旧弹窗所需订单号、状态、收货联系人/地址、数量、商品总额、运费、优惠券、会员优惠、积分抵扣、实付、时间、支付方式和备注；`user` 仅含昵称及推广人昵称；`cart_items` 仅含商品 ID、名称、快照分类名、规格、单价、数量和安全图片 URL。不存在的快照分类或单价返回 `null`，不会由现价或现分类编造。商品最多200行，单行快照64 KiB、整单512 KiB；错 UID、重复申请、损坏 JSON 或超限均拒绝整个完整订单信息响应。退款或旧金额异常本身不放宽或阻止已验证申请的只读订单信息；付款和归属始终必须通过。

`invoice.view` 可读，`invoice.manage` 可处理；普通 `order.view/manage` 不授予开票权限。处理携带申请行 ID、状态（`-1/0/1`）、发票号、备注、行版本和 UUID 请求键。服务端先锁支付主单，再锁来源订单及发票申请，重验 UID、拆单归属、支付和退款代次、有效票据历史、当前净支付金额及版本；处理结果与管理员回执同事务保存。已开票必须提供8至20位数字发票号，未开票或拒绝须清号；发票金额不由表单决定。提交结果未知时页面保留原请求，不自动重发，只重新读取核对。

历史 0.00 申请仅在仍为待开/拒绝、没有号码，且存在匹配的创建时快照、没有已开或未核验历史时，才能在同一锁内从当前净额补为实际金额。安装前缺失创建基线的历史记录保持只读，不能据订单现在的金额反推过去的开票事实。曾报告出票或票号的不可变数据库留痕不因后来清号、拒绝或软删而消失；退款侧继续依据该留痕拒绝不安全操作，这不代表税务平台验真。

旧页的完整订单弹窗已有独立 `invoice.view` 后端读取合同和前端只读订单/商品区域，发票类型与抬头类型也按旧表格语义在当前已加载页筛选。旧 chart 请求具备全量状态统计合同，但模板未渲染该统计；当前页计数不等于全量统计。旧全字段搜索还覆盖邮箱、地址、银行和用户昵称/手机号，七类新搜索字段不等于旧全字段范围。历史 0.00 无基线需要人工核验，因此逐屏状态为 `partial`。管理状态不代表税务平台已上传、电子票已交付或红字发票已办结；这些渠道及真实角色、生产数据和发布验收继续开放。平台 Admin 本批不扩张到 Supplier 或 Kefu 发票权限。

当前逐屏判定、路由/API 分布和本机验证记录分别见 `audit/admin-legacy-user-order-route-parity-invoice-followup-20260928.json`、`audit/route-distribution-invoice-followup-20260928.json`、`audit/admin-frontend-api-contracts-invoice-followup-20260928.json` 与 `audit/invoice-member-record-followup-acceptance-20260928.json`。前批日期快照保留原字节。

上线前需用实际开票回执规模检查请求键查询：目前 `store_order_status` 先按有索引的 `change_type` 缩小范围，再对 JSON 文本中的 UUID 做前置通配匹配，代价随同类回执数量增长。5 秒语句期限会在超限时拒绝处理，不能据此宣称生产容量已经验收；若真实体量接近期限，应先改用带唯一约束和可索引请求键的回执存储。
