## 来源与持久化边界

`PurchasedProductLabelCodec` 捕获真实付款事件、付款根单、实际履约订单、用户、财务门店、供应商和购物行身份；保留赠品、旧空 SKU、原字符串购物车 ID 与 smallint 业务类型。最多 200 行，UTF8 紧凑 JSON 上限 131072 字节，数量和、重复身份、额外字段、继承属性、访问器与稀疏数组均检查。输出脱离原输入并冻结。

来源中不保存当前选定的商品标签，以便后续独立任务执行时读取配置。`paymentSourceHash` 必须由后续真实作者从完整不可变付款来源计算并重新核对；它与整个 intent 的 `source_hash` 分别表示付款来源和任务来源摘要，两者均不构成调用权限。

| 表 | 用途 | 保护 |
| --- | --- | --- |
| `purchased_product_label_intent` | 每个付款根单／实际履约订单唯一的来源 | 唯一事件键、真实 Outbox 外键、有限 JSON 结构；禁止 UPDATE、DELETE、TRUNCATE |
| `purchased_product_label_state` | 发送、处理租约、失败、死信与重放计数 | 与 intent 外键关联；可变状态独立存储；尚未授予运行权限 |
| `purchased_product_label_result` | 唯一成功回执的位置 | task ID 与来源摘要复合外键；禁止 UPDATE、DELETE、TRUNCATE |

数据库 JSONB 文本容量为 196608 字节，以容纳紧凑 JSON 转换后的空白；应用捕获的 131072 字节边界仍需执行。SQL 检查只证明结构，不证明订单付款、来源摘要正确、标签授予或完整业务回执。未来作者仍须进行全部业务核验和结果编码。

## 显式维护

`installPurchasedProductLabelStorage` 要求显式 `{purchasedProductLabels:true}` 和精确 `{database,maintenance}`。它在 PG16 实际维护 LOGIN 的读写事务中使用独立维护锁，固定有限超时并锁住真实父表，整体创建或整体回滚。重复调用仅锁定、核对和返回，不更换对象、修复目录或补写业务数据。

目录检查固定完整列、默认值、约束、索引、触发器及双向 RI 触发器。PG 分配的内部触发器名字用约束名、触发类型与函数名规范化，避免把偶然 OID 固定为合同。实际 PG16 逻辑目录摘要：`07c2843b4efd96edb224030fcff3505c5fea6e0d2668b9712679c8cc0b0d19c1`。另行检查所有者、表／列／函数权限、跨 schema 同名前缀、额外依赖与函数附件。运行时不创建 DDL，也不从当前服务端生成期望摘要。

没有给 App、Admin、Manager、Financial 或 PUBLIC 授予这三张表的能力；通用通知事件白名单、历史迁移、现有促销标签作者与运行权限计划均保持原文件。新增本地 PG16 文件有两处显式准入，原预算未变。历史源码读取只剥离经完整字节数、SHA256 和 Git blob 检查的两条准入行，原证明、旧断言和原生执行入口继续保留。

## 后续接通的必要条件

真实付款分配事务必须从实际子单和购物行建立 intent，核对完整父事件，排除无用户的合法访客，且不得对已完成的历史付款补建任务。独立消费者需要读取当前商品配置和 type5 活动附加标签，按已批准范围只追加缺失会员关系，并在同一事务写入不可变成功回执和完成状态。重复完成不得重新读取配置或重新授予后来移除的会员关系。

启用前仍需显式运行权限后继、完整业务结果编码、Queue／扫描器／重试／受控重放，以及真实付款、供应商拆单、门店、赠品、组合、并发配置修改、失败回滚和重复消息的原生业务验收。本批原生验收仅证明结构、目录、权限和回滚。旧 PHP 未上传，未部署；远端完整 Worker CI 固定旧 PHP 提交缺失的问题仍需另行处理。
