# DB-009G2：热点、多租户引用验收边界

保留完整ORM生成的表、CHECK、外键、标识列和现有索引；只在专用本机/CI随机数据库播种。
本项不是生产数据清理许可，也不默认批准新增六列宽索引或修改统计目标。

## 覆盖分母

`work-composite-foreign-key-plan.test.ts` 从模型清单选出所有12个只有窄首列候选的六列外键，
并对固定12个业务夹具名做集合相等校验。原有每子行不同事件的12项保持不变；另增加12项：

- 每表100003行，租户fixture的事件1与租户other的事件2各50000行。
- 事件3/4各一行，分属两个租户；事件5另有一行。
- 两个租户均有真实无引用父事件。支持表同样分别播种两个租户，允许复合键中的数字ID相同。
- 每个外键执行8种完整六列谓词，分别记录custom和强制generic计划，精确验证行数。
- 热点/稀疏父记录各做DELETE及键更新，要求准确报告目标外键；无引用父操作实际执行后回滚。
- 操作前后比对父子整行指纹、目标表全部约束/索引目录及列统计状态，禁止以移除约束通过测试。

## 如何解释代价

| 探针 | 含义 | 不能外推的结论 |
|---|---|---|
| 合法无引用父、稀疏引用父 | 观察真实父键分布下的选择性和generic计划 | 一次ANALYZE不证明普遍稳定 |
| 热点引用，返回50000行 | 无上限完整谓词诊断，验证多子行和真实行锁查询 | 不能当作RI触发器实际需要读取50000行 |
| 已存在的错误租户与另一租户事件ID组合 | 验证完整谓词不会跨租户返回行，并观察过滤代价 | 不等于数据库里存在这种不匹配的父键 |
| 真实父DELETE/键更新 | 验证RESTRICT/NO ACTION实际生效 | 外层EXPLAIN的触发器记录不是嵌套查询计划 |

PostgreSQL 16 `ri_PerformCheck` 对SELECT检查传给SPI的行数上限为1；因此不把无上限诊断
替代真实RI执行，也不自行加SQL LIMIT并宣称规划完全等价。
[PostgreSQL官方源代码](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/utils/adt/ri_triggers.c)。

## 真实RI内部计划增量（2026-09-12）

`work-foreign-key-index-plan.test.ts` 在专用PG16随机库的独立连接中加载auto_explain，
按官方支持的NOTICE/JSON捕获嵌套查询，启用实际行数与块计数，关闭逐节点计时与参数日志。
模块只加载该连接，所有设置为SET LOCAL；12次真实父DELETE/键更新均结束于ROLLBACK。
不改线上日志配置、不重启本机服务、不添加SQL LIMIT替代RI。
[PostgreSQL 16 auto_explain官方文档](https://www.postgresql.org/docs/16/auto-explain.html)。

本机PG16.15四项测试全部通过（51.45秒），双类型通过，隔离数据库/schema/角色零残留。
wcao_client_fk捕获12份完整内部查询计划：auto/custom/generic各含热点和无引用父键的DELETE/UPDATE。
6次引用拒绝精确核验23503及约束名，6次无引用操作成功后回滚；父子行指纹、外键、索引和统计目录保持。

- auto/custom热点实际返回1行、2块；无引用0行、2块。
- generic热点实际返回1行，但Bitmap Index Scan先读取100000项，合计89块；不能由输出一行推断启动工作量小。
- 本次最后默认统计样本下generic无引用为2块；前面五次ANALYZE的独立诊断仍有两次扫描100003行/4001块，不抹除之前三次全扫描的历史证据。
- auto阶段每种RI语句只有两次调用，不证明长连接自动切换generic后的表现；强制模式只用于诊断。

完整证据`audit/work-fk-nested-ri-20260912.json`。本增量只覆盖wcao的真实内部计划，
不替代另外15个目标的嵌套计划、默认缓存热身/多次采样、真实运行身份与规模、生产保留/统计策略。

## 默认缓存热身与重复采样增量（2026-09-12）

前条只有短auto序列；现新增5个独立连接/统计样本，每个连接明确断言初始plan_cache_mode=auto，
不设置force模式。完整事务内默认ANALYZE，先DELETE后UPDATE，各按父键1×6、4、2、4执行9次，
每次以保存点回滚，最终回滚采样事务；逐样本验证全部列统计目标和pg_statistic原样恢复。
样本间新建连接以清空RI缓存，样本内保留真实重复调用缓存。

本机PG16.15四项测试通过（52.80秒）、双类型通过、隔离库/schema/角色零残留。
本增量捕获90份实际内部计划（70次精确拒绝、20次无引用成功后回滚），不是手写PREPARE替代RI。
5个样本均在第6次DELETE观察到Plan节点中的参数符号；随后的UPDATE共用同一连接，
已从参数化计划开始，不能称其为独立冷启动序列。参数化计划识别不检查始终带参数的Query Text。
[PostgreSQL官方计划缓存规则](https://www.postgresql.org/docs/16/sql-prepare.html)。

| 默认统计样本 | 热身后的实际RI行为 | 验收含义 |
|---|---|---|
| 2/5样本，corp/client估计均只有一个不同值 | 无引用扫描100003行/4001块；稀疏引用先过滤100000行/4002块 | 默认auto下已真实复现，不能视为只存在于强制generic的假设 |
| 其余3/5样本 | 无引用2块、稀疏4块；热点位图先处理100000索引项/89块 | 索引选择性改善不消除热点启动代价 |

以上比例只是本次五个随机样本的观察，不是生产发生概率。数据是极端热点并把稀疏行放在物理末端，
不据此宣称生产延迟。数据、外键、索引、统计目录均保持，线上没有修改。
完整证据`audit/work-fk-default-cache-20260912.json`。默认缓存是否会触发风险已获得肯定证据；
下一步仍需评估统计候选策略的实际RI效果、采样成本和适用规模，以及其余15个目标的内部计划。
不能仅用提高STATISTICS后的独立SELECT结果关闭G2，也不以该测试替代自身Linux CI。

## 统计候选规模比较：显式执行入口

配置专用本机`TEST_FINANCE_POSTGRES_URL`后，在workers-ts运行：

```powershell
npm run audit:work-fk:statistics-scale
```

`scripts/audit-work-fk-statistics-scale.ts`只接受固定规模100003/1000003和默认、1000、10000三档，
每档5个新连接/ANALYZE样本，初始plan_cache_mode必须为auto。不接受额外作用域/连接参数，
不读DATABASE_URL，禁止PGlite/远程/生产回退；使用既有安全辅助创建并核验专用随机PG16库。
本入口是显式容量实验，不自动加入普通单元测试，Linux CI的类型通过不等于运行过此实验。

完整ORM的45个外键与所有CHECK/索引保留；按10000行分批播种，每语句仍有30秒时限。
每个样本的统计目标变更和ANALYZE均在回滚事务内，父DELETE逐次保存点回滚；
默认档不执行ALTER，所有档均不强制custom/generic。六次热点热身后测无引用、物理末端稀疏、再次无引用。
记录ANALYZE VERBOSE的实际采样量、墙钟耗时、表/索引字节及真实RI计划；计时包含诊断开销，
按固定顺序执行并非冷热缓存随机试验，不当作生产基准或三档延迟排名。

逐样本比对列统计目标/选项和pg_statistic恢复，结束比对全模型约束/索引以及三表整行哈希汇总。
百万行汇总使用每行哈希再汇总，避免拼接整表JSON超过单值大小限制；不是逐行导出的历史源端对账。
脚本最终成功输出WORK_FK_STATISTICS_SCALE_AUDIT才表示两个规模及清理均完成，进度行不是验收通过。
1000/10000只是候选诊断，不会自动新增生产迁移、更改保留策略或改造业务约束。
