# Temporary authority maintenance adapter

This is a local preparation template. It has not been deployed and does not authorize a production schema change. It is never imported by the main API. The template contains no usable audit token, expiry or source/SQL pins and is server-side `APPLY_ARMED=false`.

The Worker fixes database/owner/app/Admin to `postgres` / `postgres` / `cinashop_app_v1` / `cinashop_admin_v1` and uses only the existing three Hyperdrive bindings in its separate config. No HTTP path, query, body or header can supply another target. The SQL digest covers the full original v1 table/functions/triggers/revokes, both exact Admin GRANTs, and both v2 CHECK replacements. The internal native-test helper derives GRANT text from its explicit isolated fixture target; the HTTP target always remains fixed.

Only authenticated `GET /preflight`, `GET /postflight` and armed `POST /apply` exist. Authentication requires a lowercase 64-hex `X-Audit-Token` whose SHA-256 matches the configured digest and a future absolute millisecond expiry no more than 15 minutes away. Source SHA, SQL digest and run marker are also mandatory. Every POST in InspectOnly mode fails before body or database work. Apply additionally requires exact `X-Migration-Operation: admin-authority-install-v1-and-legacy-v2` and `X-Preflight-SHA256` matching the approved nonzero hash.

An apply body must be absent or have exact `Content-Length: 0` and terminate after no more than 31 empty chunks. The 32-read budget includes EOF. Nonempty chunks, conflicting framing, transfer encoding, locked/errored/stalled streams and aborts fail before database access. Pending reads have a 250 ms limit; cancellation is never awaited.

Preflight uses an owner repeatable-read read-only transaction and separate app/Admin LOGIN connections. Each runtime connection checks the actual database, current/session/backend role, PG16, read-only mode and replication origin, then the unchanged full runtime-profile auditor. The current profile dynamically recognizes the independent newcomer addon; readiness has no fixed table-count assumption.

Approval binds source/SQL/target, stable catalog/ACL/profile evidence and staff/role/menu/existing-receipt row digests. It excludes run marker, arming mode, backend PID and transaction-mode differences. Ordinary cart/order/queue data is excluded from the approval gate. Only the actual public catalog supplies table identifiers, which are quoted. Snapshots return catalog/data hashes, names and counts; they never return business rows or function bodies. Catalog census supports at most 2,048 ordinary persistent public tables. Authority-table row hashing supports at most 1,000,000 rows per table; every query has a 5 s statement timeout and a 1 s lock timeout. Unsupported table kinds, incomplete digests and excess bounds fail closed.

Apply makes one real read-committed owner transaction. It takes the existing advisory/staff/menu/receipt barriers, rechecks the approved evidence inside that transaction, calls the v1 and v2 `InTransaction` installers in order, and verifies the complete final profiles and exact v2 catalog. Missing/drifted/orphan objects and unreviewed default grants are refused. Historical profiles are never repaired or widened. Existing exact v2 is a no-DDL repeat. There is no whole-shop blocking lock or claim of an atomic whole-shop data snapshot. Optional `wholeData` inspection is a local/native read-only observation, has the same census/row/time bounds, and does not enter HTTP approval.

A successful POST reports its returned transaction result. Any unconfirmed POST outcome is `unknown`; this Worker makes no retry. Read-only postflight separately classifies actual addon state (`absent`, `v1`, `legacy-admin-v2`, `orphan`, `drift`) and checks all three connections. An exact postflight catalog alone cannot prove whether a previously lost response belonged to a committed transaction. HTTP errors contain only stage/status/SQLSTATE, never the original query, connection string or cause.
