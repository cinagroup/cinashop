# Temporary authority maintenance adapter

This is a local preparation template. It has not been deployed and does not authorize a production schema change. It is never imported by the main API. The template contains no usable audit token, expiry or source/SQL pins and is server-side `APPLY_ARMED=false`.

The Worker fixes database/owner/app/Admin to `postgres` / `postgres` / `cinashop_app_v1` / `cinashop_admin_v1` and uses only the existing three Hyperdrive bindings in its separate config. No HTTP path, query, body or header can supply another target. The SQL digest covers the full original v1 table/functions/triggers/revokes, both exact original Admin GRANTs, both v2 CHECK replacements, both v3 CHECK replacements, and the sole new `Admin DELETE(public.system_role)` GRANT. App ACLs remain unchanged. The internal native-test helper derives GRANT text from its explicit isolated fixture target; the HTTP target always remains fixed.

The reviewed deployment intent is account `7ea8e46d8210bad342fa7595f7935fea`, with existing bindings `HYPERDRIVE_MAINTENANCE=9748c294e21c49a99579c9cef70102e0`, `HYPERDRIVE=ba7faa6680cd48d4b3a1d36a7a5fc8f7`, and `HYPERDRIVE_ADMIN=446e94a4de0143f58c8e5178ec55db8b`. This fixed deployment scope is included in approval evidence and the config pins the account. It is control-plane intent, not a runtime proof of Cloudflare account/binding identity derived from a connection string. Before any separately authorized production action the actual provider account/resources must be independently checked. Actual database LOGIN identities and profiles are checked separately by the adapter.

Only authenticated `GET /preflight`, `GET /postflight` and armed `POST /apply` exist. Authentication requires a lowercase 64-hex `X-Audit-Token` whose SHA-256 matches the configured digest and a future absolute millisecond expiry no more than 15 minutes away. Source SHA, SQL digest and run marker are also mandatory. Every POST in InspectOnly mode fails before body or database work. Apply additionally requires exact `X-Migration-Operation: admin-authority-install-v1-and-legacy-v2-and-legacy-role-v3` and `X-Preflight-SHA256` matching the approved nonzero hash. Old v2 operation/SQL/source approval is not authority for the new v3 action; fresh full-scope approval is required.

An apply body must be absent or have exact `Content-Length: 0` and terminate after no more than 31 empty chunks. The 32-read budget includes EOF. Nonempty chunks, conflicting framing, transfer encoding, locked/errored/stalled streams and aborts fail before database access. Pending reads have a 250 ms limit; cancellation is never awaited.

Preflight uses an owner repeatable-read read-only transaction and separate app/Admin LOGIN connections. Each runtime connection checks the actual database, current/session/backend role, PG16, read-only mode and replication origin, then the unchanged full runtime-profile auditor. The current profile dynamically recognizes the independent newcomer addon; readiness has no fixed table-count assumption.

Approval binds the new operation, target catalog `legacy-role-v3`, fixed deployment intent, source/SQL/database target, stable catalog/ACL/profile evidence and staff/role/menu/existing-receipt row digests. It excludes run marker, arming mode, backend PID and transaction-mode differences. Ordinary cart/order/queue data is excluded from the approval gate. Only the actual public catalog supplies table identifiers, which are quoted. Snapshots return catalog/data hashes, names and counts; they never return business rows or function bodies. Catalog census supports at most 2,048 ordinary persistent public tables. Authority-table row hashing supports at most 1,000,000 rows per table; every query has a 5 s statement timeout and a 1 s lock timeout. Unsupported table kinds, incomplete digests and excess bounds fail closed.

Apply makes one real read-committed owner transaction. It takes the existing advisory/staff-role/menu/receipt barriers through actual COMMIT, rechecks the approved evidence inside that transaction, then dispatches from the exact locked state: addon absent runs v1→v2→v3, exact v1 runs v2→v3, exact v2 runs v3, and exact v3 runs only the full v3 `InTransaction` wrapper's no-DDL repeat validation. The v2 installer is never called on v3. Skipped v1/v2 results are `null`; v3 returns its actual installer result. All complete final profiles and exact v3 are verified; unexpected protected-data or existing-receipt changes throw and roll back. The two CHECK replacements and sole new Admin role DELETE GRANT commit together. Missing/drifted/orphan objects and unreviewed default grants are refused. Exact v3 missing its DELETE and v1/v2 with premature DELETE are refused, never repaired. App grants, old receipt shapes, functions/triggers/ownership and fixed historical profiles remain unchanged.

Addon absent is not an empty-database commissioning path: all historical whole-shop profiles and objects must already be exact. There is no whole-shop blocking lock or claim of an atomic whole-shop data snapshot. Optional `wholeData` inspection is a local/native read-only observation, has the same census/row/time bounds, and does not enter HTTP approval.

A successful POST reports its returned transaction result with target/from/to catalog and actual v1/v2/v3 stage results. Any unconfirmed POST outcome is `unknown`; this Worker makes no retry. Read-only postflight separately classifies actual addon state (`absent`, `v1`, `legacy-admin-v2`, `legacy-role-v3`, `orphan`, `drift`) and checks all three connections; it reports ready only for exact v3 and all exact profiles. An exact postflight catalog alone cannot prove whether a previously lost response belonged to a committed transaction. HTTP errors contain only stage/status/SQLSTATE, never the original query, connection string or cause.


## Fixed v2 adapter for the staged runner

`AdminAuthorityV2MaintenanceWorker.ts` and `admin-authority-v2-maintenance.wrangler.jsonc` preserve the bounded `AuthorityV2` runner phase. Its operation is `admin-authority-install-v1-and-legacy-v2`, digest is `adminAuthorityV2InstallSqlSha256()`, and exported SQL is `ADMIN_AUTHORITY_V2_MAINTENANCE_SQL`. It accepts only exact absent/v1/v2, skips completed installers, stops at exact v2, and refuses v3. Its fingerprint binds that operation and target catalog `legacy-admin-v2`; combined-v3 and standalone-v3 approvals cannot authorize it. The combined adapter above retains its original config and full v3 behavior. All adapters require matching physical-primary hashes, exact profiles and unchanged protected data. An absent receipt table must become empty and the table census must increase by exactly one; existing catalogs keep the same census.

## Fixed v3 adapter

`AdminLegacyRoleMaintenanceWorker.ts` and `admin-legacy-role-maintenance.wrangler.jsonc` use the same three fixed Hyperdrive bindings, authentication, expiry, request framing and pin variables. The operation header is exactly `admin-legacy-role-install-v3`. Its SQL digest is `adminLegacyRoleInstallSqlSha256()` and covers `ADMIN_LEGACY_ROLE_OPERATION_UPGRADE_SQL` plus the sole `GRANT DELETE ON TABLE public.system_role TO "cinashop_admin_v1";`. The production SQL is exported as `ADMIN_LEGACY_ROLE_MAINTENANCE_SQL` for an independent digest comparison.

V3 preflight accepts only exact `legacy-admin-v2` or exact `legacy-role-v3`; absent/v1/orphan/drift states fail closed. V3 postflight additionally requires exact `legacy-role-v3`. For an already confirmed exact v3 baseline, use the v3 adapter directly; the v1/v2 phase deliberately refuses v3. Apply takes the same advisory/staff/menu barriers and an exclusive receipt lock in one read-committed owner transaction, rechecks the approved catalog, all ACL profiles, protected data and physical primary hash, then installs the two CHECK replacements and the Admin-only `system_role DELETE` grant. It requires identical protected data digests and table census after installation. Existing exact v3 is a no-DDL repeat with the same catalog digest. Existing receipt rows retain the same immutable update/delete/truncate triggers. No business-row or receipt-row DML, backfill, sequence change, owner change or historical profile repair is included.

## Execution gates and order

1. Freeze the clean source commit, all three compiled Worker bundles, lockfile and the three distinct installation SQL digests. Require native PG16 rollback/receipt/ACL evidence, HTTP guard tests, independent review and the exact candidate's full Linux CI before executing the reviewed runner. Keep tokens and connection strings out of arguments, stdout, receipts and logs.
2. Read and pin the Cloudflare account, formal API deployment/version and binding fingerprint, all three Hyperdrive IDs, their current `modified_on` values and their physical destination/database/user mapping. App, Admin and maintenance Hyperdrive caches must all be disabled. A cache-enabled maintenance config blocks production preflight. Require the three roles to map to the same current primary with their fixed distinct login identities. Any live drift stops execution.
3. Deploy `AdminAuthorityV2MaintenanceWorker.ts` using `admin-authority-v2-maintenance.wrangler.jsonc` under one owned random temporary name in InspectOnly mode with a <=15-minute hash token and fixed source/SQL/run pins. Read `/preflight`; it must be ready in exact `absent`, `v1` or `legacy-admin-v2` state, with all three current primary hashes matching. Validate unauthenticated refusal and InspectOnly POST refusal. Store only the sanitized exact receipt and fingerprint in an immutable local evidence record.
4. Arm only that reviewed source/SQL operation and approved nonzero fingerprint. Issue one strictly empty `POST /apply` with the exact v1/v2 operation header. The server reopens fresh independent app/Admin LOGINs and verifies their evidence again under the owner transaction's locks. Require the returned committed result and a fresh read-only `/postflight` showing exact v2 and unchanged protected staff/menu data before progressing. On a lost/503 response, record unknown and inspect read-only; never automatically repeat the POST.
5. Delete the owned v1/v2 temporary Worker and verify both control-plane absence and public 404. For v3, deploy a separately owned InspectOnly Worker and obtain a new exact preflight/fingerprint; the v1/v2 fingerprint cannot approve v3. Repeat the same arming, one-POST, read-only postflight and cleanup sequence with `admin-legacy-role-install-v3`. Require exact v3, unchanged table count and every protected receipt/staff/role/menu digest.
6. Independently recheck all three Hyperdrive cache/mapping pins, the unchanged formal deployment/bindings and absence of owned temporary Workers. Any deployment failure may still leave a Worker; cleanup must inspect ownership even if CLI exit is nonzero. A successful production migration is not a formal API/Pages deployment or a real least-privilege-role acceptance result; those release gates follow separately.

Both installers roll back automatically when a precommit verification throws. Once committed, do not drop the permanent evidence table or rewrite immutable receipts as a rollback; any recovery needs a separately reviewed forward operation. Neither adapter accepts SQL, target role/database, row IDs or replacement catalog definitions from an HTTP request.

## Fixed orchestration runner

`scripts/run-admin-addon-maintenance.ps1` requires exactly one of `-InspectOnly` or `-Apply`, an explicit `-Phase AuthorityV2` or `-Phase LegacyRoleV3`, the clean source SHA, that phase's installation SQL SHA, and the current formal API version plus 31-binding metadata SHA. Apply additionally requires the independently reviewed, nonzero `-ApprovedPreflightFingerprint`; an inspection fingerprint cannot approve a different phase. Cloudflare credentials stay in the process environment. The runner generates its own short-lived token and never prints it.

Before deploying a temporary Worker it verifies the inert template, Wrangler 4.131.0, complete Worker inventory, fixed Hyperdrive route/LOGIN/cache configuration and formal baseline. After deployment it checks the exact version annotation, all three Hyperdrive bindings and all seven ephemeral plain-text pin values before any database read. Each CLI command runs hidden with a 60-second deploy / 30-second delete deadline and at most 64 KiB per output stream. A bounded-process failure stops execution; uncertain descendant termination prevents automatic Worker deletion and cannot produce a successful cleanup receipt. Owned CLI output and Wrangler logs are removed separately.

The runner makes no retry of the armed apply POST. Its authentication check also sends one deliberately invalid POST without the operation header; that request is rejected before any database access and is not an apply attempt. Every successful Apply run requires independent read-only postflight. Every successful run requires ownership-checked deletion, control-plane and public 404, no maintenance-prefix Worker, unchanged formal version/bindings and unchanged Hyperdrive route/cache/modified timestamps. Receipts live in the clean checkout's ignored `.cache/<random-worker-name>/receipt.json` and contain only bounded, sanitized evidence. `scripts/test-run-admin-addon-maintenance-offline.ps1` verifies the runner using local mocks and inert Node processes; it sends no network or database request.
